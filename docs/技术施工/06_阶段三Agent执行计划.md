# 第三阶段执行计划

2026-10-03，用户明确要求继续完成第三阶段。依据《综合项目规划书》第 6、7、8 章和技术施工报告第 18 节，在原工作区保留一二期数据继续施工。

目标：一个经营主体、两家模拟门店，把组合交易、代表性售后、跨期结算和调拨差异处理到可解释的终态。采用现有 React/FastAPI/PostgreSQL 模块化单体与独立 HTTP Mock，不增加基础设施或依赖。

## 业务设计与约束

- 组合交易只是关联和汇总已有销售、受理、安装及售后事实；各子单保留独立终态。未知请求或未处理差异不能被父交易的手工状态覆盖。
- 售后按原订单行申请、店长审批，退款与货物验收分别记录。退款总额不超过各行实收剩余额度，未决申请占用额度；已出库退货核对原序列号。未出库取消只释放相应占用。不可逆已履约服务须记录人工处理依据。
- 模拟退款、通信冲正沿用持久请求号，超时查询原号，迟到/重复结果不能覆盖终态。旧通信受理若缺少可恢复的原始事实，只能明确人工核查；新增 Mock 受理保存办理前快照用于可验证冲正。
- 安装现场异常记录原因，可改约退回待派或关联售后取消；重新领料不得重复扣库存。
- 收益原单不可改写。退款按原冻结规则比例产生负向收益/提成调整；已结提成留下后续抵扣。账单标明业务归属期、结算期和是否最终结清，分期未到账不冒充少结。结算记录审批与实际模拟释放，保留原账单和差异处理依据。
- 两店使用各自角色账号，原用户仍只属于原门店；调拨只开放同经营主体下的两店相关单据。商品以明确 SKU 对应，不按同名猜测。出库后单列在途，验收到货才增加目的店库存；数量/序列号差异进入人工核查，审批后处理剩余在途。
- 盘点保存账面和实盘快照，审批时若库存已变化则要求重新盘点；差异产生独立库存流水，不能侵占已锁定的销售库存。
- 统一待办从原业务派生责任人、状态、期限和处理链接，不另造通用工作流引擎。审批期限默认两天，安装期限使用预约时间；这是演示处理规则，不宣称实际 SLA。
- 一切资金和通信操作仍为模拟。现有政策外的任意临时报价不开放；需要变价必须发布新政策并重新确认订单。

## 实施落点与接口补充

2026-10-03：主库 head `021`，Mock head `005`，实际结果见施工记录。新增组织只用于限定两店调拨；用户仍固定所属店，没有建立跨店通用访问权限。异步 Session、HTTP Mock 和现有 LangChain 适配边界不变。

| API 前缀（均 `/api/v1`） | 业务与关键约束 |
| --- | --- |
| `/transactions` | 创建、关联来源、派生状态与 `resolve-component`；原金额为子单报价合计，`received_amount` 来自成功收款，`net_amount` 扣已核实退款；相关结果未知则返回 null |
| `/aftersales` | 申请、review、receive、refund、reconcile、service-resolution、close、resolve-failure；已失败请求不能再次退库，失败终结保留回执，已退库必须履行后续退款 |
| `/reversals` | 原成功受理的独立冲正审批、提交和原号核对；原受理终态不改写 |
| `/installations/{id}` | 新增 issue、cancel，改约后复用原领料；取消明确记录耗材实际退回及未退回情况 |
| `/finance` | 原账单增加 earning_period / line_key / is_final；新增 cases、settlements、owners；调整与结算行独立不可变，负余额在员工后续结算先抵扣 |
| `/transfers`、`/inventory/counts` | 同主体对应 SKU、单商品分次收货、在途/损失分列；审批核对盘点快照，保留设备历史归属 |
| `/todos` | 原单派生待办、期限及跳转；按岗位和门店筛选，无独立可随意完成的工作流状态 |

主库迁移 017—021 与 Mock 004—005 采用新增结构、旧数据回填和明确约束。金额 NUMERIC、原请求号唯一、库存短事务和行锁、不可变触发器沿用既有模式；外部 HTTP 期间不持有行锁。演示扩展与升级都保留旧成功/未知结果，备份同一 PostgreSQL 快照同时覆盖两种数据库角色可见的数据。
